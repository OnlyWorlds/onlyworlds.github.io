title: Profiles
description: "The extension profiles: named fields and reading rules on the standard's types that every tool reads the same way, published in schema-dist."
---

A profile is a convention on the standard's types: a named extension field, or a rule for reading the fields the standard already has, that tools agree to read the same way. Each is a page in schema-dist's [`profiles/`](https://github.com/OnlyWorlds/schema-dist/tree/main/profiles) folder, beside the schema. Each entry below names the serial that first carried it: a serial is one numbered release of schema-dist ([its tags](https://github.com/OnlyWorlds/schema-dist/tags)). A new profile's field is named `x_<profile>_<field>`.

Three have pages of their own: [Messages](/docs/schema/profiles/messages), [Addresses](/docs/schema/profiles/addresses) and [Lenses](/docs/lenses).

## What every reader does

### Identity

**[`x_identity_key`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/identity.md)**: the same being in several worlds. Two Characters or Creatures carrying the same UUID are one being; a value that is not a UUID means nothing, and a tool that lets people add their own fields reserves the `x_identity_` prefix.

### Calendar

**[`atlas_calendar`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/calendar.md)**: a world's own calendar, the names it gives its time line. It changes no date. Read by Atlas, the TypeScript SDK, the Python package and the Unity SDK; it keeps its name from before the profile grammar. Version 2 (serial 68) adds a leap rule's exceptions and offset, enough for the Gregorian calendar.

### Charter

**[`x_charter_of`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/charter.md)** (since serial 82): marks a Law with supertype `Charter`, a Construct with supertype `Guide` or one with supertype `Domain` as one of the world's reading aids, read by its presence (any value but null, a string only when something is left after trimming, and since serial 126 an empty list or an empty object is absent, so a full and a compact read of one element agree); the value names the world it was written for. A tool's front door shows the aids first and its lore views leave them out; the same pair without the mark is lore (a kingdom's charter in a novel). Only a keeper writes the mark. The TypeScript and Python SDKs read it as `isCharterElement` / `is_charter_element` (4.98.0, 0.80.0). Since serial 135, in a world where a reader finds a Charter, an Object or a Construct whose subtype is `in design` or `locked` (trimmed, in any case) is a design part in that state, whatever its supertype.

### Strand

**[`x_strand`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/strand.md)** (since serial 98): a world in miniature, one story small enough to hold in one look, named on the World. The value is an object of three ids, `{"narrative": …, "event": …, "location": …}`: a Narrative (the story), one of the Events in its `events` (the happening) and one of the Locations in that Event's `locations` (where it happened). The hero is the story's `protagonist` and where the hero is now is the hero's `location`, so five slots rest on four links the standard already has. Only the story is required: `event` and `location` may be null or absent, a strand begun whose other slots are the next thing to make. Any other shape of the value is no mark: an empty string in any of the three members, the story's included, or a number or an object in `event` or `location`. No reader trims a member: a string of white space alone, or an id with a space on it, is a string that names no element, so its slot is empty. A reader answers the five slots as one reader sees the world, plus whether then and now are the same place; a slot it cannot fill stays empty, never filled from another, and an empty slot is the next thing to make, not an error. The TypeScript and Python SDKs read it as `strandOf` / `strand_of` (4.119.0, 0.97.0; the strand begun 4.120.0, 0.98.0), and the front door's selection as `charterOf` / `charter_of` (4.100.0, 0.82.0).

### Room

**[`x_room_of`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/room.md)** (since serial 45): a parlor is a chat room on a world, and it keeps its lines, board entries and work inside the world as ordinary elements. This mark tells them apart: it holds the id of the world the room belongs to, or of the workshop session (a sitting) it was made in; a sitting's own mark holds the world's id, and a sitting names its winning spec in `x_star`, the spec's id (since serial 118). With one of ten type-and-supertype pairs it makes a room element, which a lore view (a list, search, a graph) leaves out unless asked and a public view never shows; the TypeScript and Python SDKs export `ROOM_PAIRS` and `isRoomElement` / `is_room_element`. The pairs, each compared trimmed and without regard to case: Narrative `Message` (a line in the room), Narrative `Board` (a board entry), Narrative `Report` (a report, since serial 112: below), Relation `Work item` (a packet of work), Construct `Spec` (a workshop's spec), Relation `Heart` (one person's heart on a spec or an item), Relation `Take` (one member's take on a work item, which also carries `x_room_item`, the item's id), Relation `Vote` (one person's ranked picks), Event `Sitting` (a workshop's sitting) and Character `Member` (a member's card in the room). The mark, not the word, makes the room: a Narrative with supertype Message and no `x_room_of` is lore and stays in view. Since serial 83 the mark is read by its presence, as `x_charter_of` is: any value but null, a string only when something is left after trimming; since serial 126 an empty list or an empty object is absent, and `false` still counts. Since serial 135 a line in the room that names an Object in its `objects` or a Construct in its `constructs` is in the talk on that element, whichever sitting it was said in, and a report is shown with the talk on each Object and Construct it links.

### Message

**[The message](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/message.md)** (since serial 72): no field of its own, the one definition of a message's addressing, its sender's proof, the read mark, the thread and the Note beside it, as [Messages between members](/docs/schema/profiles/messages) says.

### Checks

**[`x_checks_rules`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/checks.md)** (since serial 47): a work world's house rules as a machine can check them, on the Charter beside the text a person reads: the world's Charter as the [charter profile](#charter) selects it: the newest marked Charter. Each rule is its sentence plus one check from a closed set (a field present, a text matching a pattern, a link field holding at least n ids, a value from a list), scoped by type (one, or a list) and optionally supertype or subtype; a reader reports how many elements each rule scoped and which fall short, and names by name any rule it cannot apply (a list naming a type the schema does not know, a field one listed type lacks, a pattern outside the regex subset Python and JavaScript share), never passing it silently. A known-of stub is judged by no rule: its missing fields are unknown, not short (since serial 64 the fixture holds two stub cases, a bare one and one with its fields filled, so every reader is tested on it). A field is present when it is not null, not an empty list, not an empty object (since serial 126), and, for a string, something is left after trimming, the whitespace being the room profile's White_Space set, so a unit separator alone is present (said since serial 118, which also adds two rules a team's world keeps: every work item and every report carries the room's mark). The Python package's doctor reads it from 0.24.0, from the Charter only since 0.28.0.

### Names

**[`x_names`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/names.md)** (since serial 48): a world's own words for the 22 types, on the World. In a work world a Character shows as *Employee*, an Institution as *Team*. Only what a person reads changes: the API, the folder, its directory names and every id keep the standard's names, and a tool that never reads the map shows Character as always. A folder's `world.json` carries it. The TypeScript and Python SDKs' `typeWord` / `type_word` give the word to print.

### Spine

**[`x_spine_*`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/spine.md)** (since serial 55): a world that maps a software ecosystem, what is built, the contracts it speaks, where each thing lives and who keeps it. Each kind is an element type with a supertype from a closed list (`Package`, `Repo`, `Profile`, `Charter`…); ownership is a Title with supertype `Seat` and the elements it links; thirteen `x_spine_*` keys carry what no field holds (address, truth, access, status, layer, audience, depends on, probe, what the probe last read, verified, the keeping seat's name on a public projection, the projection's source on its World, and the row a retirement Event retires). It counts days from 2012-01-01 and ships the calendar that reads them. The Python package reads it (`read_spine_element`); its 46 fixture cases are the test.

### Packet

**[`x_packet_*`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/packet.md)**: a packet of work about a world, a Relation with supertype `Work item` listing elements with a reason each (`x_packet_elements`), the world they belong to (`x_packet_source`), the tool that made it (`x_packet_producer`: its `tool`, and its `version` only when known, never invented; a producer with no `tool` is ignored) and, optional since serial 112, whom it is for by role (`x_packet_for`: a list of Title ids, beside `actor`, the one person it is for; not a link, so no lens reaches a work item through it); the Relation's own link fields carry the same elements, and the subtype is its state (`open`, `taken`, `done`, and since serial 136 `standing`), matched trimmed and in any case. A standing work item is a kept order of work, never done and never open work, and an item with no state is never open work either. Since serial 136 `x_packet_from` names the Character who asked for the work, never guessed from its maker. The [Python doctor](/docs/development/python#check-a-world)'s `--packet` prints its findings in this shape.

### Report

**[`x_report_answers`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/report.md)** (since serial 112): a report is what a session, or a closed talk, leaves behind in a world: what was done, what was found, and what changed in the world because of it. It is a Narrative with supertype `Report` carrying the room's mark `x_room_of`, so it sits in the world's working layer beside messages and work items, never in its lore; a Narrative with supertype `Report` and no mark is lore. It is made in two steps: the reporter's AI hands it in (`subtype` `handed in`, its whole text as `story`, its own Character as `narrator`), and the keeper's AI completes it (`completed`: `description` the short human part, links to what it touched, `consequences` a line per change, which may name the element it changed by its address (rule 8)). A keeper reporting its own session writes it once, born `completed`, and sets the work items it answers to `done` once the work exists (since serial 115). The reporter is the seat the platform names as the report's maker (`created_by` on onlyworlds.com), and `narrator` the Character it speaks as; a reader served no `created_by` takes the narrator's Character. `x_report_answers` lists the work items it answers, each also in `relations`; a work item in `relations` and not in the key is touched, not answered. The TypeScript and Python SDKs count a marked report as a room element through `ROOM_PAIRS`. A report that continues earlier work names the first report of that work as its `parent_narrative`, while a closed talk's report keeps its board entry there; a reader groups reports by that parent, read as written and never walked further up (rule 9, since serial 120): `reportThreadsOf` in [TypeScript](/docs/development/typescript-readers#report-threads), `report_threads_of` in [Python](/docs/development/python). Each line of `consequences` is read one way (rule 10, since serial 129): the text splits at every carriage return and line feed, a line's address is the last that names an element of this world, and the address leaves the shown words only when nothing the writer wrote is lost; the profile's second fixture, `report-lines.fixture.json`, holds every reader to it: `readReportLines` in [TypeScript](/docs/development/typescript-readers#report-lines), `read_report_lines` in [Python](/docs/development/python).

### Review

**[`x_review_*`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/review.md)**: two marks on any element. `x_review_proposed` (`by`, `evidence`, `expires`) on a new element written as proposed, shown apart from settled elements until a keeper acts (an empty value, `""`, `[]` or `{}`, is no mark: the API refuses a write carrying one with `422` [`review_mark_empty`](/api/errors/#review_mark_empty), and reads a stored one as absent, since 2026-10-29); `x_review_checked` (`by`, `at`, `against`) says who last confirmed it true, when, and against what. **A mark's `by` is the writer's own word for who made the mark** (since serial 116): a claim, never proof of who wrote the mark or the element. It is read as stored, never trimmed: a `by` that is not a string, or is whitespace alone, names nobody, and whitespace around a word or an id makes it neither. A reader shows it as the mark's word ("the mark names Ada"), never as a fact ("proposed by Ada"); it puts a name in its place only where its platform resolves the value to a member of the world or to its owner (ids compared as ids), or where the value is the id of a Character of the same world, said as that Character, and shows any other `by` as its raw value, apart. Who wrote an element comes from what the platform recorded, never from `by`. A writer writes the id its platform gives it; on onlyworlds.com that is its `membership` from `GET /me`, and the world's owner, who has none, writes the exact word `owner`. On onlyworlds.com a writer below co-builder sets a mark's `by` only to its own membership id, exactly as `GET /api/v2/me` gives it, or sends the mark back exactly as the element holds it; any other `by` is refused with `403` [`review_by_another`](/api/errors/#review_by_another) (since 2026-11-11). A proposed change to an existing element is a [proposal](/docs/development/api/proposals) beside it, not this mark. The TypeScript and Python SDKs read the mark with `proposedMarkOf` / `proposed_mark_of` and `handsOnAsProposed` / `hands_on_as_proposed`.

### Record

**[`x_record`](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/record.md)** (since serial 102): a game's run kept in the world its Characters live in, so a character carries what they did from run to run. The run is an Event carrying the mark `x_record`: `tool` (the game's id in the tools list's form) and `played_at` (when it was played, a real calendar instant written as `2026-11-01T00:30:00Z`; since serial 123 it is read by the [message profile](/docs/schema/profiles/messages)'s time grammar, so a lower-case `t` and `z`, an offset and no zone read, and a time without its seconds is no record) are required; `version`, `seed` (a string), `outcome` (one lowercase word, 1 to 24 letters, such as `won` or `sunk`) and `seats` (a Character's id to the seat in the game's own words) are optional. Anything else in the value is no mark. The game keeps its own tally beside it under its own prefix, which the profile never reads. Who took part is the Event's `characters`, and nothing else. A Narrative that lists the Event in `events` and names a Character as `protagonist` (a story about them) or `narrator` (their own account) is that Character's story of the run. A run or a story still proposed is not read until a keeper settles it. A game writes the run and never edits an existing element: a character's experience is read from their records, never written into their fields. The recommended words are `Record` as the Event's supertype and the game's word as its subtype (`Battle`, `Crossing`); no reader keys on them. The TypeScript and Python SDKs read a Character's records, newest first, as `recordsOf` / `records_of` (4.124.0, 0.100.0).

### Landing

**[The landing](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/landing.md)** (since serial 103): the first picture of a world wherever a visitor arrives at it, such as an account's OnlyWorld on onlyworlds.com's landing. It adds no field. It reads the graph the [lens profile](/docs/lenses) defines for the visitor, so it shows exactly what they may see and nothing more. A real world shows its most-linked Characters, each with the elements one link away. A small world, with fewer elements in the visitor's graph than a size (24 by default), shows its gaps first: orphans and near-orphans, a Character whose `location` names no Location in the visitor's graph, and a Location no Character's `location` names. Any door may serve the answer, keyless or signed in, each read from the graph that door's reader is served; a key beside the five (onlyworlds.com's `baked`, its `lenses`) is the door's own and outside the profile, so a reader reads the five and passes the rest through. The packages' reader is `landingOf` in TypeScript and `landing_of` in Python (4.127.0, 0.102.0).

### Map space

**[Map space](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/map-space.md)** (since serial 105): how a reader turns a world's Maps, Zones, Markers and Pins into geometry. It adds no field and stores nothing; the standard already says what each field means, and this page states the reading once, with a fixture of 43 cases. It reads the elements as the reader is served them, so a hidden Zone and its Markers are not in a member's or a visitor's input and never come back. The answer has four parts, `{ maps, zones, pins, out }`, its coordinates whole numbers in the Map's pixels:

- `maps`: each Map's frame (`width`, `height`, `depth`, `z_max`, `scale`, `location`, `parent_map`). `scale` is metres per pixel, read from `x_metres_per_pixel` when the Map carries a positive number there, else `null`. A `width` or `height` that is a whole number is answered as written, 0 and a number under 0 included (since serial 137). A Map whose `width` or `height` is missing or not a whole number reports the extent of its own placed points there (a point whose zone or map is not served, or without a whole `x` and `y`, measures nothing), marked `extent: "points"`, and `null` when it has no placed point of its own.
- `zones`: one outline per Map a Zone has placed Markers on, its points taken from the Markers in `order`, then by id. `shape` closes it as a `polygon` or leaves it a `line`; empty, absent or any other value reads as `polygon`, `Line` included.
- `pins`: each Pin's point, with the element it stands for as `element_type` and `element_id`, both `null` for a Pin with neither or only one of the two.
- `out`: what the reading left aside, counted by reason: `no_point`, `no_markers`, `dangling`, `no_map`.

`x` and `y` count from the bottom left. `z` is a point's elevation upward, never a height: a Marker at `z` 300 sits 300 pixels up, and a `z` that is missing or not a whole number reads as 0. A `z` past the Map's `depth` is kept as written, and the Map's `z_max` shows the overrun. Two rows of one type with one id read as the last one served, and `type` is read as written: `Map` is no Map. The packages' reader is `mapSpace` in [TypeScript](/docs/development/typescript-readers#map-space) and `map_space` in [Python](/docs/development/python#what-it-covers) (since 4.129.0 and 0.104.0; serial 106's rules since 4.129.1 and 0.104.1).

**Layout maps** (since serial 110, the same page's rules 8 to 10). A Map is a layout map when it carries `x_layout`, an object whose `method` is a non-empty string: its Pins were laid out by that method, or by hand when the method is `"hand"` (a board). The mark is that key alone, never the supertype or a missing picture. `x_layout.settings.ground` `{map, width, height}` names the Map the layout stands on; a ground naming no served Map, or the layout Map itself, is no ground. A Pin with `x_hand: true` on a layout map was placed by hand, and a new lay-out keeps it where it is; only `true` marks it, and on a Map that is not a layout map the mark means nothing. A writer that gives a Map with Pins a method marks every Pin first, then writes `x_layout`. The layout reading answers, for one Map, `{layout, ground, hand}`: the method or `null`, the ground Map's id or `null`, and the ids of the Pins a new lay-out keeps (every Pin of a board), in code point order. Its fixture holds 32 `layout_cases` beside the 43. A row without a non-empty string id is no element, and a link whose value is an empty string is no link, read as null (written whole in serial 126). **Reading changes nothing** (since serial 132, rule 8's end): the stored Pins are the layout, and a tool that draws a stored Pin draws it where it stands. Reading or drawing a layout map adds, changes or removes none of its Pins or Markers and leaves its frame and its `x_layout` as they are: laying it out again, or placing on it the elements it does not place, is a write like any other, never something a tool does by itself as a Map is opened or drawn. A method word is read whole (`by-kind-2` is not `by-kind`), and `by-kind`, `around` and `by-links-3d` are the [default layouts](#default-layouts) page's. **Picking a Map** (since serial 119, rule 11): which Map stands for the world's space when a world has several stays the tool's, but a layout map is never a candidate: a tool that picks one, by whatever rule of its own (no `parent_map`, the most Pins, a picture, a name, the order read), reads each Map's layout first and leaves every layout map out. A Pin on a layout map is where its element stands in that drawing, and a Marker there where its Zone's outline runs in it, never where either is in the world, drawn over a ground or not: a tool that measures between elements or places one in the world reads no Pin and no Marker of a layout map. A world whose every Map is a layout map has no Map for its space, and a tool says so. The map-space reading and the layout reading still answer a layout map, its Pins and its Markers; the rule is on the tool that picks or places from their answers.

**A child Map's parent frame** (since serial 139, the same page's rules 13 and 14). A Map that shows part of another says where it lies on the Map its `parent_map` names with `x_parent_frame`, a list of four numbers `[x0, y0, x1, y1]`: two corners of a box in the parent's pixels, from its bottom left. The child's rectangle lies on that box, each axis by its own ratio, so a box of another shape is a stretch and never a fault. A point on the child is carried to its parent as `x0 + ((x * (x1 - x0)) / width)` and `y0 + ((y * (y1 - y0)) / height)`, in 64-bit floats and in that order, one level at a time up the chain, and the walk says why it ended: `top`, `dangling`, `cycle`, `no_frame` or `no_carry`. A frame on a Map with no `parent_map`, one that is not four numbers, and one that is not a box are each named. The fixture's 66 `frame_cases` hold it; the map-space reading is unchanged. Read by the TypeScript SDK's [`carryOf`](/docs/development/typescript-readers#a-child-map-on-its-parent) and the [Python package](/docs/development/python)'s `carry_of` (since 4.183.0 and 0.137.0).

### Default layouts

**[The default layouts](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/layout.md)** (since serial 132): ways to draw a world nobody has laid out. `by-kind` lays out a whole graph, each kind of element at its own place round a circle, links drawing elements together; `around` lays out one element and what is linked to it, on rings; both read the graph alone. `by-links-3d` (since serial 137) lays out a whole graph in three dimensions by its links and the world's Maps and Pins: the most linked elements become centres with their groups round them, the Map that holds the most of the graph by a Pin is a flat plate under them, every other piece of linked elements is laid out the same way on a ring round the main one, and an element linked to no other and pinned on no map is left unplaced. A tool can hand an earlier answer's points back to keep a picture still. They add no field and store nothing: each is a method word for a [layout map](#map-space), so a Map whose Pins were made by one can say so. The same graph gives the same points in every tool and every language, `by-kind` to the last bit, `around` to within 1e-12, and `by-links-3d` to the last bit for its centres, grouped and pinned elements off the ring and within a billionth of a rest for the rest. A method's word is its version: a change that moves any point is a new method with a new word, never a silent change to an old picture. `unplaced` is the one reading of which elements a saved layout map has no Pin for, so every tool that tells how many, or lists them, says the same. The fixture beside the page holds 17 `by-kind` cases, 10 `around` cases and 17 `unplaced` cases, and `by-links-3d` has its own fixture of 116 cases with its table of directions. Read by the TypeScript SDK's [`layoutByKind`, `layoutAround`, `unplacedByKind` and `unplacedAround`](/docs/development/typescript-readers#a-worlds-default-picture) and [`layoutByLinks3d` and `unplacedByLinks3d`](/docs/development/typescript-readers#a-world-laid-out-in-3d), and the [Python package](/docs/development/python)'s `layout_by_kind`, `layout_around`, `unplaced_by_kind`, `unplaced_around`, `layout_by_links_3d` and `unplaced_by_links_3d` (the pieces since 4.182.0 and 0.136.0).

### Import map

The import map is not a field at all, but a table an import tool reads when it brings a world in from another tool.

**[The import map](https://github.com/OnlyWorlds/schema-dist/blob/main/profiles/import-map.md)** (since serial 67): for each source tool, the words its users write for their own categories, each mapped to one of the 22 types (`city` to Location, `organization` to Institution). LegendKeeper's table is the first. An import tool offers the table and applies it only on the user's yes; it never types anything silently. The [Python package](/docs/development/python)'s LegendKeeper door reads it since 0.58.0.

## On onlyworlds.com

- **[`x_charter_of`](#charter)**: the front door ([`front_door`](/docs/development/api/members#the-front-door)) names the Charter the profile selects, the newest marked Charter, and serves the three aids as [`reading_aids`](/docs/development/api/members#reading-aids).
- **[`x_names`](#names)**: onlyworlds.com stores it on the World since 2026-10-23.
- **[`x_strand`](#strand)**: onlyworlds.com stores it on the World and serves it only to a reader who can see the story it names (a story known only by name counts), so a guest or a stranger who cannot gets no key; the owner and co-builders read it as stored (since 2026-10-31). The front door serves the reading itself: [`reading_aids.strand`](/docs/development/api/members#reading-aids) on `GET /me` and an agent's join reply holds the six slots as the key reads the world, all of them `null` when there is no strand in its view (serial 100). The world page's Overview draws it after the Charter, Start here and the Domains, an empty slot as "Not yet".
