A tool can sign a person in through onlyworlds.com instead of asking for their email and password. The tool sends the browser to onlyworlds.com, the person signs in there (and the first time presses Continue), and the browser comes back to the tool with a code. The tool trades the code once for an `ow_a_` [account token](/docs/getting-started/keys#account-tokens). The tool never sees a password.

<SigninSteps />

It is OAuth 2.1's authorization code flow with PKCE (`S256`), for public clients: no client secret, no refresh token, no scopes. The token is an ordinary account token, with the same reach as one the person mints themselves. It adds a door and replaces nothing: email and password, and world keys, keep working.

## Registered tools

Only a registered tool can sign a person in. `GET /api/v2/auth/clients` lists them, with no credential:

```bash
curl -s "https://www.onlyworlds.com/api/v2/auth/clients"
```

{/* shape: GET /api/v2/auth/clients */}
```json
{ "clients": [ { "id": "atlas", "name": "Atlas",
    "redirect_uris": ["https://atlas.onlyworlds.com/signin/callback"],
    "native": false } ] }
```

{/* shape: GET /api/v2/auth/clients clients[] */}
| Field | Meaning |
|:--|:--|
| `id` | The `client_id` the tool sends |
| `name` | The tool's name, as the Continue page and the token's name show it |
| `redirect_uris` | The exact return addresses: a `redirect_uri` must equal one of them byte for byte, except a native app's loopback ones (below) |
| `native` | `true` for a desktop or mobile app, `false` for every other tool |

The answer is sent `Cache-Control: public, max-age=60`, so a removed address stops being served within a minute. The list is kept by OnlyWorlds; no route adds to it.

**Return addresses.** A web tool's are exact `https://` addresses. A native app's (RFC 8252) may also be:

- **a loopback address**, `http://127.0.0.1/<path>` or `http://[::1]/<path>`, listed with no port. The app picks its port when it runs, and a `redirect_uri` on the same host and path matches with any port from 1 to 65535. `localhost` is never accepted: a name can resolve somewhere else.
- **a custom scheme**, matched exactly: a reverse-DNS scheme such as `com.example.app://callback`, or a known app's (`obsidian://`). `http`, `https`, `javascript`, `data` and `file` are never a custom scheme.

One native app is registered: the [Obsidian plugin](/docs/tools/obsidian-plugin) (`obsidian`, shown as OnlyWorlds Builder), with `http://127.0.0.1/onlyworlds-signin` and `obsidian://onlyworlds-signin`. Since plugin 3.15.0 it signs in this way on desktop, through the loopback return; on a phone the button is hidden until the `obsidian://` return has been walked there.

## Sending the person to sign in

The tool sends the browser to `https://www.onlyworlds.com/signin/authorize` with five query parameters:

| Parameter | Meaning |
|:--|:--|
| `client_id` | The tool's `id` in the registry |
| `redirect_uri` | One of that tool's registered return addresses, byte for byte: no tolerance for a trailing slash, a case change or an added query. A native app's loopback address takes the port it chose |
| `state` | The tool's own opaque value, up to 1024 characters, sent back untouched {/* limit: signin_state_chars */} |
| `code_challenge` | The PKCE challenge: the base64url SHA-256 of a verifier the tool keeps |
| `code_challenge_method` | `S256`. `plain` is refused |

What the person sees:

- **Signed in, and has pressed Continue for this tool before:** nothing. A `302` sends the browser straight back to `redirect_uri?code=…&state=…`.
- **Signed in, the first time for this tool:** one page asking whether the tool may sign in as them, with Continue and Cancel. Continue sends the code back; Cancel sends `redirect_uri?error=access_denied&state=…`.
- **Not signed in:** the sign-in page first, then the same.

A request onlyworlds.com cannot trust is never redirected. A missing or unknown `client_id`, a `redirect_uri` not on that tool's list, a `code_challenge_method` other than `S256` (`plain` or none), a `code_challenge` that is not 43 base64url characters, a `state` that is missing, empty or over 1024 characters, or a parameter named twice answers a `400` page on onlyworlds.com that says what is wrong, with no `Location` and no code. These checks come first, so a signed-in person gets the same page. Every answer from this page, the redirect included, is sent `Cache-Control: no-store` and `Referrer-Policy: same-origin`.

## Trading the code

The tool's return page checks that `state` is the one it sent, then posts the code once to `POST /api/v2/auth/token`, as JSON, with no credential:

```bash
curl -s -X POST "https://www.onlyworlds.com/api/v2/auth/token" \
  -H "Content-Type: application/json" \
  -d '{ "grant_type": "authorization_code", "code": "…", "code_verifier": "…",
        "client_id": "atlas", "redirect_uri": "https://atlas.onlyworlds.com/signin/callback" }'
```

{/* shape: POST /api/v2/auth/token request */}
| Field | Meaning |
|:--|:--|
| `grant_type` | `authorization_code` |
| `code` | The code from the return address |
| `code_verifier` | The PKCE verifier, 43 to 128 characters, whose S256 hash was the `code_challenge` {/* limit: signin_verifier_min_chars signin_verifier_max_chars */} |
| `client_id`, `redirect_uri` | Exactly as the authorize request sent them |

{/* shape: POST /api/v2/auth/token */}
```json
{ "token": "ow_a_…", "token_id": "…", "token_type": "bearer", "expires_at": null, "account": { "id": "…", "username": "…" } }
```

The answer is sent `Cache-Control: no-store`. `expires_at` is when the token stops working, for a tool whose registration asks for a lifetime (1 to 720 hours; Little Lens's tokens last six); null for one with none, whose token works until it is revoked. An expired token is refused as a revoked one is, the same 401. `token` is shown only here: the tool keeps it and sends it as `Authorization: Bearer ow_a_…` on the [account routes](/docs/getting-started/keys#account-tokens), such as [managing members](/docs/development/api/members#managing-members), and to [read a world's elements](/docs/getting-started/keys#reading-a-world-with-an-account-token) as the person's own access there, with no key minted. On the person's account page, under Account tokens, it is listed by the tool's name and the browser (`Atlas on Firefox`), and they can revoke it there. `token_id` (since 2026-10-25) is the token's id: a tool done with the token revokes it with `DELETE /api/v2/account/tokens/{token_id}`, sending the token itself as the bearer. That revoke ends the tool's consent only when it was the tool's last live token for the person, or for a tool that asks each time ([Consent and revoking](#consent-and-revoking)). {/* limit: signin_token_lifetime_max_hours */}

**A code lives 60 seconds and is spent by its first exchange,** whether that succeeds or fails. A code sent again is refused and also revokes the token its first exchange minted: a replayed code is treated as a stolen one. So take `code` out of the address bar before the exchange, and send the exchange before any other request: a reload would spend the code on a refusal. {/* limit: signin_code_seconds */}

## Errors

| Status | Code | When |
|:--|:--|:--|
| `400` | [`invalid_grant`](/api/errors/#invalid_grant) | The code is unknown, used, expired, or was issued for another `client_id`, `redirect_uri` or `code_verifier`. One body for every case, byte for byte. Start the sign-in again |
| `422` | [`invalid_request`](/api/errors/#invalid_request) | The body is not JSON (a form-encoded body included) or not an object, a field is missing or not text, or `grant_type` is not `authorization_code`. `param` names it. A code in a form-encoded body or a JSON object is spent |
| `429` | [`rate_limited`](/api/errors/#rate_limited) | Too many sign-in attempts from this address: this route and the password sign-in share one count, 40 in 5 minutes. Wait the `Retry-After` seconds. The body is not read, so the code is not spent {/* limit: signin_attempts */} |
| `429` | [`too_many_requests`](/api/errors/#too_many_requests) | Over the request budget, as on every route ([Limits](/docs/development/api-reference#limits)) |

The authorize page's refusals are pages, not API errors: see [Sending the person to sign in](#sending-the-person-to-sign-in).

## Consent and revoking

The Continue page appears once per account and tool. After that, the tool's sign-ins pass with no page until the consent ends, which happens in three ways:

- **The tool's last token revoked.** Revoking a token a tool got through Sign in with OnlyWorlds, on the account page or with `DELETE /api/v2/account/tokens/{token_id}` (the [TypeScript SDK](/docs/development/typescript)'s `revokeAccountToken`, since 4.122.0, by the `tokenId` the sign-in answered), revokes that token only (since 2026-10-25). The consent ends when the person holds no other live token from that tool's sign-ins; then its next sign-in shows the Continue page again. So a tool can replace its token, signing in again and revoking the old one, without being asked again. A tool whose registration asks for it keeps the consent through its own sign-outs, whatever its tokens: one that holds its token in memory only and revokes it when you leave, such as Little Lens, does not ask you to Continue on every visit; only Disconnect ends its consent (since 2026-10-27). The revoke a replayed code causes counts the same way.
- **Disconnect.** The account page lists, under Tools you signed in to, every tool with a consent or a live token, with its count of live tokens and a Disconnect button. Disconnect revokes every live token the tool's sign-ins hold for the account and ends the consent, and every live world key the tool minted with those tokens (2026-10-26), kept keys included; tokens and keys minted by hand, on the site or by other tools are untouched. With an account token it is `DELETE /api/v2/account/clients/{client_id}` ([below](#disconnecting-a-tool)).
- **A tool taken off the registry.** It loses every person's consent at the next deploy of onlyworlds.com. If it is ever listed again, each person is asked again.

**The keys a token minted** (since 2026-10-27). Revoking a sign-in token also revokes the world keys it minted, in any world, in the same step, unless the person holds another live token of the same tool: then the keys pass to the tool's newest token and go with its last. Three kinds of key outlive the token: a key minted with `keep: true` on `POST /api/v2/account/worlds/{world_id}/keys` (a tool that stores a key on the device, such as Atlas or Lantern, passes it, and takes the key back when the world leaves the device); the keys of a token made by hand or through a password sign-in (the Obsidian plugin's); and the keys of a tool that asks each time. A world's first key, minted with the world, records no token and is never swept. A sign-in code used twice takes every key its token minted, kept or not. `GET /api/v2/account/tokens` gives each token's `keys_minted`, its live keys.

**A tool that asks each time.** The [Council](/docs/tools/council) and [Tactical Tangle](https://tangle.onlyworlds.com) need their token only to mint a world key, then revoke it, and the registry marks them as asking each time: any revoke of one of their tokens ends the consent, so a token left behind (a tab that closed first) never keeps it. They show the Continue page on every sign-in, and the page says so. The mark is the registry's own; `GET /api/v2/auth/clients` does not serve it.

What ties a token to its tool is how it was minted, never its name. Revoking a token you minted by hand on the account page changes no consent, even when it is named like a tool's. A token a tool mints for itself with `POST /api/v2/account/tokens` is not one of its live tokens either: to replace its token without losing the consent, a tool signs the person in again. Revoking a token that is already revoked withdraws nothing.

### Disconnecting a tool

```bash
curl -s -X DELETE "https://www.onlyworlds.com/api/v2/account/clients/atlas" \
  -H "Authorization: Bearer ow_a_…"
```

{/* shape: DELETE /api/v2/account/clients/{client_id} */}
```json
{ "client_id": "atlas", "tokens_revoked": 2, "keys_revoked": 1 }
```

`200` with how many live tokens and world keys it revoked, `0` and `0` on a repeat: it is safe to send twice. `client_id` is the tool's `id` as [the registry](#registered-tools) lists it; one that cannot be an id (lowercase letters, digits and dashes, at most 40) is `422` [`invalid_request`](/api/errors/#invalid_request). The bearer may be one of the tool's own tokens, so a tool can disconnect itself: that token is revoked with the rest.

## In the SDK

The [TypeScript SDK](/docs/development/typescript) has both halves, from 4.46.0, on a client with no key (`new OwV2Client()`):

- **`signInWithOnlyWorlds({ clientId, redirectUri, resume, storage })`** mints `state` and the verifier, keeps them under the client id in `storage`, and sends the browser to the authorize page (`navigate: false` only returns the URL). `redirectUri` is the registered address as a string, never built from `location.origin`: a web tool's `https:` one, or, since 4.104.0, a native app's loopback address with the port it bound (`http://127.0.0.1:53682/<path>`) or its own scheme, exactly as registered. `localhost`, a loopback without its port, a query and a fragment are refused before anything is sent. A native app passes `navigate` a function that opens the system browser. `resume` is small JSON the tool wants back after the redirect, such as an open link or a pending join code.
- **`completeSignIn({ clientId })`** runs on the return page. It checks `state` and that the page is the registered address, takes `code` and `state` out of the address bar, trades the code, and returns `{ token, tokenId, expiresAt, tokenType, account, resume }` (`tokenId` since 4.73.0 and `expiresAt` since 4.94.0, each null from a server that does not send it; `expiresAt` is null too for a tool whose tokens have no lifetime). A refusal is an `OwSignInError` whose `reason` is `state_mismatch` (nothing was sent), `invalid_grant`, `rate_limited`, `offline` or `failed`.

`storage` is any object with `get`, `set` and `remove`. It defaults to the browser's `sessionStorage`; in Node it must be passed. The SDK keeps no token: the pending record is cleared once a return carries its state, on success and on refusal (since 4.104.2, a return with another state, such as a forged link to a custom scheme, leaves the sign-in pending), and the token is the tool's to store. A native app passes `completeSignIn` the address its loopback server or scheme handler received as `url`; the SDK then compares the scheme, host, port and path exactly and leaves the window's history alone. The [Python package](/docs/development/python) has no sign-in calls: a local tool signs in as a native app with a loopback return, registered for it.
